# M5 / M6 fixes — 2026-10-20

Two defects found by static analysis (deepseek scouts) and confirmed by runtime measurement.
Committed on the engine tree as `1de8ed22a`, branch `saker-fix-m5m6`; patch regenerated 549 -> 622 lines.

## M5 — `encode()` readback did not scatter (latent)

`src/llama-context.cpp`, the narrow-logits branch of `encode()` copied K floats straight into a
full-width row: no `-inf` fill, no column -> token-id remap. That is the same defect `decode()`
already fixes (there it collapsed draft acceptance to 0.084). `encode()` now rebuilds each row the
way `decode()` does.

**Latent, as expected:** MTP runs through `decode()`, and output is byte-identical before and after.

## M6 — drafting against an absent candidate list

`common/speculative.cpp` refreshes the shortlist from the target's logits. Two faults, both measured:

1. It asked `llama_get_logits_ith()` for a **batch index**. That API only answers for positions
   flagged for output; on `nullptr` the old code silently skipped the refresh, leaving the draft on a
   **stale** candidate list from an earlier round. Now uses the documented negative index
   (`-1` = last logit) with the batch index as a last resort.
2. The call actually fails at startup with
   `get_logits_ith: invalid logits id -1, reason: corrupt output buffer (j=4294967295, n_outputs=0)`
   — the target decode produced **no output rows at all**. `mtp_shortlist->ids` is zero-initialised,
   so the draft was scoring **K copies of token 0**. Added `llama_set_mtp_shortlist_enabled()`: when
   no logits are available the draft falls back to the **full head** for that round.

**Measured after:** t/s 35.12 / 34.96 / 34.94 vs 34.88 / 34.81 / 34.82 before; acceptance
bit-identical (0.71486, 0.49227, 0.50673); output bit-identical (`df8775c1`). Correctness fixes with no
performance effect.

**Residual, not fixed:** llama.cpp still logs `get_logits_ith: invalid logits id` ~6x per run, all at
0.04 s. That line is emitted by the API itself when the query fails; what changed is that we now
HANDLE the condition instead of continuing with a stale list. Silencing it needs an `n_outputs` query
before the call.

## Corrections to earlier claims

- `get_logits_ith` is **shortlist-gated** (generic 0, saker-noshortlist 0, saker-shortlist 4-6), not
  per-request, and calling it "benign" was wrong.
- It is **not** caused by the batch index being off-by-one; the real cause is `n_outputs = 0`.

## Eliminations during this work (runtime evidence, not code reading)

- **Recurrent rollback is not clamped**: `llama_memory_recurrent: 4 cells, 64 layers, 4 seqs 2 rs_seq`,
  correctly sized for `n_max 2`. Rollback depth is not the garbage mechanism.
- **No sliding window at all**: `n_swa = 0`, `is_swa_any = 0`, so `--swa-full` is moot.
- **Guard recovery is safe**: `cache_prompt: false` forces `n_past = 0`, a cold re-prefill that drops
  the slot's recurrent cell first; `continue_final_message` only changes template rendering.
- **The target graph is never narrowed**: only `graph_mtp` calls `saker_mtp_shortlist_get()`, and the
  target is `LLM_GRAPH_TYPE_DEFAULT`, so the `-inf` scatter cannot reach target sampling.

Garbage remains **unreproduced** (27 generations, 4 conditions). Leading hypothesis now: output
divergence is batch-shape numerics, not corruption — generic llama.cpp is itself non-deterministic
across reps at temp 0 (23ee -> bd8a -> 23ee).
